Updated 2026-10-09. Use this plan for implementation decisions and remaining work. The [tutorial](SAC_implementation_tutorial.md) explains mechanisms; the [execution trace](trace_ppo_and_plan_sac.md) maps them to source and records validation.

## 2. Settled algorithm and model contract

The first supported algorithm is **discrete, FP32, single-process, feed-forward SAC**. Drive's default policy action space is categorical even though the simulator consumes continuous controls. Treat the configured joint control table as one categorical set of `K` actions, not as independent categorical heads and not as a continuous SAC problem.

The actor returns logits `[B,K]`; collection samples an integer action ID and maps it to the corresponding Drive control through the actor's discrete action table. The action table follows the binding's existing ordering (`long_idx * num_lat + lat_idx`) and scale rules. Replay stores the sampled category, never the mapped control vector. Collection runs the actor only; it does not compute unused Q values. The critic returns two independent action-value vectors `[B,K]`, and the target critic is a frozen copy of the complete twin critic. Actor and critic parameters have separate ownership. There is no scalar PPO value head or target actor in this learner. `PuffeSAC` remains an independent class rather than subclassing `PuffeRL`; its constructor follows PPO's concept blocks and common attributes for config, seeding, device/determinism, modules, optimizers, counters and monitoring. Supplied online actor/critic modes are preserved; the frozen target copy uses evaluation mode. The tutorial holds the objective equations and worked examples so this plan can focus on implementation decisions.

## 3. Replay and scheduling

Replay represents complete one-step records through `add(obs, actions, rewards, next_obs, discounts)`. Initial additions append copied batches; after filling, `replace(indices, obs, actions, rewards, next_obs, discounts)` copies batches over exact selected slots, and `get_batch(indices)` returns those exact records. Index vectors are CPU `int64`. `len(replay)` reports current occupancy. The replay factory and physical storage implementation remain TODO; the contract does not require a FIFO ring. Old PPO values, log probabilities, advantages, and episode-row metadata are not part of the SAC replay contract.

Keep the run counters and batch units explicit. `global_step` counts received vector slot rows, including initial reset and masked rows; `valid_inserts` counts records actually admitted, including indexed replacements. `batch_size` (default 10,000) is the logical replay capacity and matches the default `learning_starts=10,000`; require `learning_starts <= batch_size`. The initial `evaluate()` fills replay to that capacity or stops at the received-row run budget. Later calls collect `ceil(replay_update_ratio * batch_size)` accepted valid transitions (default ratio `0.1`) or stop at the received-row budget. At each full-replay refresh, preselect one CPU `int64` permutation of the currently occupied replay indices without replacement. New valid transitions overwrite its distinct indices as they arrive. If the final receive contains more eligible records than the remaining quota, choose a uniform random subset of the needed size and discard the other completed records; still match every outcome, send an action for every received row, and count all received rows in `global_step`. Stop collection once the accepted-record quota or received-row budget is reached. A partial final refresh can still train when replay has reached `learning_starts`; below that threshold it performs no learner update.

Each `train()` call traverses the entire current replay dataset, including its mixture of retained old and newly inserted records. If `len(replay) >= learning_starts`, repeat `update_epochs` times: generate a fresh shuffled permutation of `range(len(replay))`, then read sequential minibatches of at most `minibatch_size` records, including the short final minibatch. Every minibatch uses the same SAC update. Defaults are `update_epochs=1` and `minibatch_size=256`; a full 10,000-record pass therefore processes 10,000 sampled transitions in 40 minibatches, with 16 records in the last one. There is no random-with-replacement minibatch scheduler, `replay_samples_per_insert`, or update-credit carryover. `sampled_transitions` counts records actually processed, including tail minibatches and repeated epochs.

The scaffold defaults to `gamma=0.99`; the inspected PPO Drive baseline uses `gamma=0.999`. These scaffold defaults are not tuned Drive settings. Select and record gamma explicitly when configuring a driving experiment. Preserve the configured Drive reward and timing for a controlled comparison. Any future reward transform is a separate objective choice and must be recorded.

The actor optimizer remains `self.optimizer` to match PPO. Optional cosine annealing applies to actor and critic learning rates, defaults off, and advances once per cycle that performs learner updates; alpha's learning rate remains fixed. The scheduler's nominal cycle horizon is `max(1, ceil(total_timesteps / ceil(batch_size * replay_update_ratio)))`, derived from the configured run budget and expected accepted-record refresh size. This approximates cycles because the numerator is received slot rows while the refresh quota counts eligible valid transitions. The outer loop still stops when received `global_step` reaches `total_timesteps`; the final vector receive may cross that threshold. Scheduler state carries its original horizon and continues on resume even if the run budget changes; after its horizon it stays at `eta_min`.

Raw environment statistics accumulate until logging, and profiling names follow PPO's `Profile`/`Utilization`, dashboard, uptime and SPS reporting. The 0.25-second logging cadence ends with a final-budget flush. `PuffeSAC.train()` returns `None` between emissions and carries the latest cycle's losses at an emission; only the outer run manager invokes callbacks, and only for emitted logs.

## 4. Replay collection is the first correctness gate

`PuffeSAC.evaluate()` directly owns the `vecenv.recv() -> policy -> replay -> vecenv.send()` cycle. There is no injected collector or collector callback. The current contract assumes Drive-style masks for the action that just completed and a same-receive auto-reset observation. The interface does not claim compatibility with arbitrary backends that return reset-only rows under next-step autoreset semantics.

Keep `self.observations`, `self.actions`, and boolean `self.pending` arrays indexed by actual integer slot IDs returned by `recv()`. Receive batches can be reordered or noncontiguous, so join each reward, flags, mask, pending observation, and action by that ID. The initial reset has no pending action and creates no transition. Set `pending[env_id]` when an action is sent regardless of the mask; it records whether an outcome still needs matching, not whether the completed action is eligible for replay. Preserve pending state across `evaluate()` and `train()` calls.

For each receive, preflight boundary cases for eligible pending actions before inserting any rows. Ordinary valid transitions use the returned successor and discount `gamma`. A true terminal, including a stopped or removed agent, uses zero discount and a finite placeholder derived from the saved pending observation; the reset observation belongs to the next episode. When termination and truncation coincide, termination takes precedence. A pure continuing-task truncation needs discount `gamma` and the actual final pre-reset observation. Since Drive does not currently transport that observation, the scaffold raises `NotImplementedError` before replay insertion for an eligible pure truncation; it neither substitutes the reset observation nor labels the interruption terminal.

The initial driving setup keeps `terminate_on_goal=0`, so completing an assigned goal is not currently a terminal task end. If a later run enables `terminate_on_goal=1`, the bridge must also provide a reset reason that identifies final-goal success. Capture the final observation and reason before `c_reset()` in C or Python map replacement; once the reset or replacement occurs, the old world state may be gone. Drive writes the mask before applying movement and handles goal updates later in the step, so route-goal regeneration can remove an agent after that mask/terminal pass. Keep the pending-action join, returned mask, and boundary flags distinct, and cover this late removal ordering in boundary tests.

After preflight, sample actions for the current observations, insert completed prior actions, save the new observation/action pairs under their returned IDs, mark them pending, and send controls. Replay must copy inserted batches before later sends can overwrite shared vector memory. Send actions for every returned row, including the last receive of a bounded collection cycle; those actions stay pending through `train()` and are matched on the next `evaluate()` call. The [execution trace](trace_ppo_and_plan_sac.md) and [tutorial lesson 2](SAC_implementation_tutorial.md#2-one-transition-through-replay) explain this lifecycle in detail.

## 5. Review order and remaining work

Continue the discussion in this order: `evaluate()`, `train()`, then the rest of initialization and shutdown. These are review topics, not executable integration stages: constructing the components and implementing boundary transport must precede a complete Drive training run.

| Stage | Status and next gate |
|---|---|
| **1. Evaluate: collect correct transitions** | The supplied-component scaffold owns the receive/action/send loop, mask and boundary preflight, slot-indexed pending state, batched replay insertion, and receive/insert counters. Transition semantics are unchanged by class alignment. Earlier synthetic checks covered reordered slots, reset exclusion, copied replay inputs, transitions across cycles, and fail-fast truncation handling. Still needed: connect actual Drive vecenv construction and validate mask timing, same-receive reset behavior, terminal outcomes, and the unsupported truncation path. |
| **2. Train: learn from stored transitions** | `_train_sac_transition()` checks replay warmup, then makes `update_epochs` shuffled passes over all `len(replay)` records using sequential minibatches, including the tail. Each minibatch recomputes targets and performs the critic/actor/temperature optimization, full Polyak update, counters and loss averaging. The PPO-aligned wrapper handles cycle bookkeeping. Historical update-credit checks are superseded; the current focused replay smoke is summarized in §1. Actor cosine annealing remains optional and disabled by default. Drive shape/action-ID validation and a bounded real-environment smoke remain integration gates. |
| **3. Construct models, replay, and configuration** | Still TODO. Add a Drive actor adapter that reuses the existing discrete-to-continuous mapping; build independent twin Q networks and full target copies; implement fixed-capacity replay with copied append, exact indexed replacement, and indexed batch retrieval; and add the Drive factory/config dispatch without changing PPO entry points. The supplied-component trainer requires `data_dir`, defaults `env` to `puffer_drive` and `torch_deterministic` to `false`, and exposes `checkpoint_interval=50`, `final_model_name=final_model.pt`, and `resume_state_path=None`; it does not construct those components or resume automatically. Resolve and validate action count, observation shape, replay memory, `gamma`, warmup, capacity, refresh ratio, and minibatch settings before environment reset. Seed model and replay RNGs before supplying them to the trainer. |
| **4. Complete boundary and run integration** | Still TODO for real Drive truncations and success termination. Extend C/Python/vector transport to snapshot the old final observation and reset reason before reset or map replacement, then test scenario timeout, forced reset, simultaneous termination/truncation, and late goal removal. Preserve `terminate_on_goal=0` for the initial continuing-driving setup. A real Drive run remains unsupported until this bridge exists for any eligible pure truncation. |
| **5. Close and checkpoint the first milestone** | The trainer closes vecenv/monitor, saves `data_dir/final_model.pt`, and returns its path; the outer run manager owns logger closure. Periodic actors use `models/`, best actors use `best_models/`, and best-score checks happen only on fresh emitted logs for the current epoch. Error cleanup closes resources without publishing a partial final state. `trainer_state.pt` format 5 restores actor, online/target critics, temperature, three optimizers, both scheduler states (even with annealing disabled), configuration, counters including `sampled_transitions`, best score and global RNG into compatible supplied components. It contains no update credits; older state formats are rejected. It is learner-only: restore requires fresh environment state, cleared pending arrays, and empty replay that refills before learning. It does not resume replay, action-layout metadata, or live environment state. |

The first end-to-end acceptance point is a short single-process Drive run with resolved config, constructed actor/critics/replay, valid discrete action mapping, continuing-task boundary semantics, metrics, cleanup, and learner-only checkpoint restore. Report separately which boundary cases were exercised; synthetic vecenv checks alone do not establish Drive integration or learning quality.

## 6. Deferred extensions

Continuous SAC and its squashed actor, recurrence and sequence replay, DDP, AMP/compilation, performance tuning, benchmarks/sweeps, remote logger parity, and architecture-aware C/Raylib export are later extensions. They are outside the first discrete single-process Drive milestone and should be added only with their own contracts and validation; they are not prerequisites for calling that narrower milestone complete.
